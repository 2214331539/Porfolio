# 数据库与数据模型设计

## 1. 数据库选择

主数据库使用 PostgreSQL。原因：

- 内容系统天然需要关系查询：文章-分类-标签、图文-话题-图片、简历-经历-项目。
- 支持 JSONB，适合保存 SEO、主题、导出配置等半结构化字段。
- 支持全文检索，但中文需额外分词方案（见 §7 “中文检索说明”）。
- 与 Prisma 迁移和类型生成配合稳定。

缓存与队列使用 Redis。对象文件使用 S3 兼容存储，数据库只保存元信息和访问 URL。

## 2. 通用约定

所有业务表默认包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `uuid` | 主键，数据库生成 |
| `created_at` | `timestamptz` | 创建时间 |
| `updated_at` | `timestamptz` | 更新时间 |
| `deleted_at` | `timestamptz?` | 软删除时间，核心内容表保留 |

命名约定：

- 表名使用复数 snake_case。
- 公开 URL 使用 `slug`，并建立唯一索引。
- 排序字段统一使用 `sort_order int`。
- 状态字段统一使用 `status text`，应用层使用枚举约束。
- 灵活配置使用 `jsonb`，但核心查询字段必须拆列。

## 3. 枚举

### status 与 visibility 的职责划分

`status` 与 `visibility` 是**两个正交维度**，不要互相表达对方的语义，避免判断冲突：

- `status`（内容生命周期）：内容处在创作流程的哪个阶段——草稿、定时、已发布、归档、回收站。
- `visibility`（可见范围）：**仅对 `published` 内容生效**，决定已发布内容公开到什么程度——公开、未列出（有链接可访问但不进列表/sitemap）、私密（仅后台预览）。

前台“是否可见”的判定 = `status = 'published' 且 published_at <= now()` **且** `visibility = 'public'`。因此 `ContentStatus` 中**移除 `private`**，私密语义统一由 `visibility = 'private'` 表达，单一来源。

### ContentStatus

```text
draft
scheduled
published
archived
trashed
```

### Visibility

```text
public      # 公开，进入列表与 sitemap
unlisted    # 未列出，仅凭链接访问，不进列表/sitemap
private     # 私密，仅后台可预览
```

#### 中文检索说明

PostgreSQL 默认全文检索（`to_tsvector('simple'/'english', ...)`）**不对中文分词**，直接用于中文内容会退化为整段匹配，基本失效。本项目内容以中文为主，检索方案分阶段落地：

- **MVP**：用 `pg_trgm` 扩展 + `GIN` 索引，对 `title`、`summary` 做 `ILIKE`/相似度模糊匹配，满足后台和前台的关键词搜索。不在 `content_markdown` 上建全文索引（大字段，成本高）。
- **增强**：若需要正文级中文检索与相关性排序，引入中文分词方案——数据库内 `zhparser`/`pg_jieba` 扩展，或外置 Meilisearch / Typesense 搜索引擎并由 `analytics-rollup` 类任务同步索引。

图文笔记（`notes.title` / `notes.body`）遵循同一策略。
